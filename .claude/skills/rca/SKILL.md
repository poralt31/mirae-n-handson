# 장애 원인 분석 (RCA)

대상은 `incident-logs/$ARGUMENTS/`, 결과는 `docs/rca/$ARGUMENTS.md` 다. 인자가 비어 있으면 `ls incident-logs/` 를 보여 주고 묻는다.
절을 하나 끝낼 때마다 결과 파일에 저장한다. 저장하기 전에는 매번 6단계의 마스킹을 적용한다.

## 절차

1. **수집 범위** — 파일을 통째로 읽지 않는다. `wc -l` · `ls -la` · `head`/`tail` 몇 줄로 시작한다.
   - 파일마다 기록 기간 · 줄 수 · 시각 형식 · 타임존(오프셋 표기 여부)을 표로 정리한다. 타임존이 다르면 KST 로 바꾸는 규칙을 적는다.
   - 오류 · 경고 · 5xx · 타임아웃을 분 단위로 센다(`awk` 집계). 배경 수준(평소 분당 건수)과 달라지는 시작 · 끝 시각을 정한다.
   - 앞쪽 여유를 뒤쪽보다 넉넉히 둔다. 로그가 끝나서 끝 시각을 확정할 수 없으면 "확정 불가"라고 쓴다.
2. **타임라인** — 배포 · 재기동 · 첫 오류 · 마지막 오류 같은 사건을 시각 순서로 적는다. 모든 줄에 `파일:줄번호` 를 단다(`grep -n` 으로 얻은 번호만 쓴다).
3. **가설** — 2개 이상 세운다. 가설마다 아래 셋을 적는다.
   - 근거: 무엇을 보고 세웠나
   - 반증 조건: 로그가 어떻게 나오면 틀린 것인가
   - 확인 방법: 실행할 명령
   - 대안 가설(트래픽 · 커넥션 풀 · 재기동 · 데이터 · 배포 변경)을 빠뜨리지 않는다.
4. **반증과 판정** — 로그로 확인할 수 있는 것은 실제로 실행한다. 명령과 결과 숫자를 그대로 남긴다.
   - 같은 오류가 사건 **이전**에도 있었는지 구간별로 비교한다. 엔드포인트 · 예외 · 스택 프레임 조합으로 묶는다. nginx 상태코드와 앱 ERROR 의 건수가 맞는지 대조한다.
   - 그다음 배포 이력의 변경 항목을 소스 코드 · 설정 · 시드 데이터와 대조해 연결 고리를 확인한다.
   - 판정은 **유지 / 기각 / 판단 불가(로그 부족)** 중 하나로 하고 이유를 한 줄로 쓴다. 판단 불가면 어떤 로그가 있었어야 하는지 적는다.
5. **리포트 작성** — 1~4단계 절은 남겨 두고 아래 순서로 채운다.
   - **요약**: 5줄 이내. 무엇이, 언제부터 언제까지, 원인, 확신 수준
   - **원인**: 인과 순서로 쓴다. 직접 원인과 배경 원인을 나눈다.
   - **근거 로그 줄**: 원인 서술의 문장마다 `파일:줄번호` 와 발췌를 단다.
   - **수정안**: 지금 적용할 것. 어느 파일의 무엇을 어떻게 바꿀지 제안만 한다.
   - **재발 방지**: 같은 유형을 구조적으로 막는 장치
   - **모니터링 항목**: 지표 · 임계값, 그리고 이번 타임라인에서 그 경보가 울렸을 시각
   - **확인하지 못한 것**: 판단하지 못한 이유와 다음을 위해 남길 로그
   - 수정안 · 재발 방지 · 모니터링은 서로 섞지 않는다.
6. **마스킹** — 리포트를 저장하기 전에 `.claude/skills/rca/masking-rules.md` 의 규칙을 적용한다.
   - 적용한 뒤 IP · 이메일 · 식별자 · 토큰 패턴으로 다시 `grep` 해서 남은 원본값이 없는지 확인한다.
   - 맨 아래에 "마스킹 적용: 유형별 건수" 를 한 줄로 남긴다.

## 하지 말 것

- 로그에 없는 줄을 인용하지 않는다. 줄번호와 발췌는 `grep -n` · `sed -n` 결과에서만 가져온다.
- 가장 많이 나온 오류를 곧바로 원인이라고 부르지 않는다. 사건 이전의 배경 수준과 비교하고, 대안 가설을 반증해 본 뒤에 판정한다.
- 원본 로그(`incident-logs/`)와 소스 코드를 수정하지 않는다. 수정안은 문서에 제안으로만 쓴다.
- 마스킹 대응표(원본 ↔ 별칭)를 파일로 남기지 않는다.
- 마스킹 전 원본을 임시 폴더(scratchpad · `/tmp` 포함)에 복사해 두지 않는다.
- 원인 추측은 3단계 전에 하지 않는다. 사용자가 범위만 요청하면 그 절만 쓴다.
