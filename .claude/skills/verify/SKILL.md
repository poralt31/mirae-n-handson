# 머지 전 검증

검증 대상: $ARGUMENTS

- 인자가 비어 있으면 `git diff upstream/main...HEAD` 를 대상으로 삼는다.
- 인자가 `vendor-prs/*.patch` 같은 patch 파일이면 그 patch 를 대상으로 삼는다.
- 절차는 저장소 루트의 `templates/verification-loop.md` 를, 판정 항목은 저장소 루트의 `templates/approval-checklist.md` 를 따른다. 경로는 모두 저장소 루트 기준이다.

## 반드시 지킬 것
- 코드를 수정하지 않는다. 고치기 시작하면 그 순간 "만든 쪽"이 된다. 판정과 수정 방향만 보고한다.
- 근거 줄번호(`파일:줄번호`)를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 남긴다.
- 테스트를 실행하지 않고 통과했다고 쓰지 않는다. 실행할 수 없었으면(서버 꺼짐, 의존성 미설치) 그 사실을 적고 사람에게 기동을 요청한다.
- 테스트 · 명령 출력은 통과 / 실패 수와 실패한 테스트 이름만 대화에 남긴다. 전체 로그를 싣지 않는다.

## 1. 요청 범위 확인
- 요청 범위를 한 문장으로 확보한다. 인자에 있으면 그 문장을, patch 파일이면 `Subject:` 줄을 쓴다.
- 어디에서도 확보할 수 없으면 **판정하지 말고 먼저 질문**한다. 범위를 모르는 채로 "요청 범위 이탈 없음"을 충족으로 표시하지 않는다.

## 2. 변경 파일 목록과 diff 읽기
- 목록을 먼저 본다.
  - diff 범위: `git diff --stat upstream/main...HEAD` (인자로 범위가 오면 그 범위)
  - patch 파일: `git apply --stat <patch>` 와 `git apply --check <patch>`
- 그다음 파일마다 diff 를 읽는다(`git diff upstream/main...HEAD -- <파일>`). 줄번호는 실제 파일의 줄번호를 쓴다.
- 변경 파일이 어느 폴더(`modern/api`, `modern/web`, `characterization`, 그 밖)에 속하는지 분류해 둔다. 4단계에서 쓴다.

## 3. 체크리스트 대조
- 저장소 루트의 `templates/approval-checklist.md` 를 읽는다. 항목을 여기에 옮겨 적지 말고 그 파일을 기준으로 삼는다.
- 항목마다 충족 · 미충족 · 확인 필요 중 하나로 표시한다.
- 심각도(치명 / 경고 / 제안)는 그 파일의 "심각도 정의"를 따른다.
- 컨벤션 기준은 팀 `CLAUDE.md` 와, 있으면 `convention-check` Skill 의 결과를 쓴다.

## 4. 테스트 실행
변경된 폴더의 테스트만 실행한다. 출력은 파일로 돌리고 요약 줄만 확인한다.

| 변경된 폴더 | 명령 (저장소 루트에서) |
|---|---|
| `modern/api` | `cd modern/api && ./gradlew test` |
| `modern/web` | `cd modern/web && npm test` |
| 이관 코드(레거시 기능을 옮긴 변경, `characterization/lib` 변경 포함) | `cd characterization && npm test` (레거시 대상)<br>`cd characterization && TARGET_BASE_URL=http://localhost:8080 npm test` (새 API 대상) |

- 의존성이 없으면 `npm ci` 로 설치한다(`npm install` 금지).
- characterization 은 레거시 컨테이너와 새 API(8080)가 떠 있어야 한다. 응답이 없으면 실패로 세지 말고 "실행 불가"로 적은 뒤 사람에게 기동을 요청한다.
- 기록할 것은 실행한 명령, 통과 수, 실패 수, 실패한 테스트 이름뿐이다.

## 5. 승인 기준 판정
- 네 기준(테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수)을 하나씩 판정한다.
- 하나라도 미충족이면 반려한다. "실행 불가"나 "확인 필요"로 남은 기준은 충족으로 표시하지 않는다.
- 이슈가 0건이면 경고 · 제안 수준까지 한 번 더 훑고 나서 판정한다.

## 6. 출력 형식 (순서 고정)

```
판정: 승인 | 반려

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 | 실행 명령과 통과 · 실패 수, 실패한 테스트 이름 |
| 치명 이슈 0건 | 충족 / 미충족 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 | 위반 이슈 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
|---|---|---|---|---|
```

- 이슈 한 건은 심각도(치명 / 경고 / 제안) · `파일:줄번호` · 근거 · 수정 방향 네 칸을 모두 채운다.
- 표 아래에 "확인 필요" 항목을 `파일 — 이유` 형식으로 짧게 덧붙인다(없으면 생략).
