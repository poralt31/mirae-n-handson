# 레거시 모듈 문서화

## 반드시 지킬 것
- 분석 대상 폴더(`$ARGUMENTS` 의 모듈 경로, 보통 `legacy/` 아래)의 파일은 **읽기만 한다.** 수정 · 생성 · 삭제하지 않는다.
- 외부 라이브러리(`vendor/`, `node_modules/`), 빌드 산출물(`target/`, `build/`)은 읽지 않는다.
- 모든 항목에 근거를 `파일:줄번호` 로 붙인다. 직접 열어 확인하지 못한 것은 추측으로 채우지 않고 "미확인"으로 적는다.
- 주석과 코드가 다르면 코드를 기준으로 쓰고, 다르다는 사실을 비고에 남긴다.

## 0. 대상과 모듈명 정하기
- 첫 번째 인자 = 모듈 경로, 두 번째 인자(선택) = 범위 제한(예: "검색 · 등록 검증만"). 범위가 있으면 그 밖은 다루지 않는다.
- `<모듈명>` 은 폴더 이름이 아니라 아래 셋 중 하나다. 표에 없는 경로면 멈추고 사용자에게 묻는다.
  | 모듈 경로 | 모듈명 |
  |---|---|
  | `legacy/item-bank-php` | `item-bank` |
  | `legacy/assignment-thymeleaf` | `assignment` |
  | `legacy/grade-mssql` | `grade` |

## 1. 계획 먼저 제시 (분석 시작 전 멈춤)
- 단계마다 읽을 파일과 순서, 건너뛸 폴더, 위험해 보이는 지점(지나치게 긴 파일, SQL 이 섞인 화면 파일 등)을 제시한다.
- 사용자가 계획을 승인하기 전에는 파일 내용을 분석하지 않는다(목록 확인 · `wc -l` 정도만).

## 2. 진입점 → 3. 의존 관계 → `ARCHITECTURE.md` 저장
- 진입점 표: URL 또는 화면 이름 / 처음 실행되는 파일 / 그 파일이 부르는 주요 함수 / 근거.
- 의존 관계: "A → B (A가 B를 호출)" 형식. 포함(include · import)과 호출을 구분한다. mermaid flowchart 1개 + 호출 표.
- 가장 긴 함수 3개: 파일, 함수 이름, 시작 · 끝 줄, 하는 일 한 줄.
- 저장: `docs/<모듈명>/ARCHITECTURE.md` — 모듈 개요(5줄 이내) / 폴더 구조 / 진입점 표 / 의존 관계 / 가장 긴 함수 3개 / 미확인 목록. 저장한 뒤 다음 단계로 넘어간다.

## 4. 데이터 흐름 → `ERD.md` 저장
- 먼저 방금 저장한 `ARCHITECTURE.md` 를 읽고 시작한다.
- 테이블 목록: 테이블 / 주요 컬럼 / 근거(스키마 파일 또는 SQL 문이 있는 파일:줄번호). 스키마는 `db/mariadb/init/*.sql` · `db/mssql/init/*.sql` 에서 확인한다.
- mermaid erDiagram 1개. 외래 키로 선언된 관계는 "선언", 코드의 JOIN 에서 추정한 관계는 "추정"으로 표시한다.
- 읽기 · 쓰기 위치 표: 테이블마다 SELECT 하는 함수, INSERT · UPDATE · DELETE 하는 함수(파일:줄번호).
- 저장: `docs/<모듈명>/ERD.md`. 저장한 뒤 다음 단계로 넘어간다.

## 5. 비즈니스 규칙 후보 → `BUSINESS-RULES.md` 저장
- 규칙마다 아래 형식을 그대로 쓴다. ID 는 `BR-01` 부터.
  ```
  ### BR-01
  - 규칙: (한 문장)
  - 근거: <모듈 경로>/<파일>:<시작줄>-<끝줄>
  - 근거 코드:
      (코드 1~3줄 그대로 인용)
  - 확신도: 확실 | 추정 | 미확인
  - 비고: (매직 넘버, 주석과 코드 불일치, 범위 한계 등)
  ```
- 확신도 "확실" 은 인용한 코드만으로 규칙이 성립할 때만 쓴다. 뷰 · 프로시저 · 다른 모듈 정의에 기대면 "추정".
- 문서 끝에 "주석과 코드가 다른 곳" 표(위치 / 주석 / 실제 코드 / 규칙 ID)를 둔다.
- 저장: `docs/<모듈명>/BUSINESS-RULES.md`.

## 하지 말 것
- **존재하지 않는 함수를 쓰지 않는다.** 함수 이름은 Grep 으로 정의 줄(`function 이름`, 메서드 선언, `CREATE PROCEDURE`)을 찾은 것만 적는다.
- **호출 방향을 뒤집지 않는다.** "A → B" 는 A 파일 안에 B 를 부르는 줄이 있을 때만 쓰고, 그 줄을 근거로 단다. include 한 쪽과 include 된 쪽을 바꿔 적지 않는다.
- **코드에 없는 규칙을 만들지 않는다.** 주석 · 변수 이름 · 화면 문구 · 일반 상식만으로 규칙을 쓰지 않는다. 인용할 코드 줄이 없으면 규칙이 아니다.
- 근거 줄번호를 기억으로 적지 않는다. 인용 직전에 Read 로 그 줄을 다시 확인한다.
- 없는 기능(예: 수정 화면이 없는데 "수정 시 검증")을 채워 넣지 않는다. 없으면 "범위 한계"에 적는다.

## 6. 사람이 표본 점검할 규칙 3개 추천
- `BUSINESS-RULES.md` 저장 후, 사람이 코드와 직접 대조할 규칙 3개를 골라 이유와 함께 보고한다.
  1. **가장 그럴듯한 규칙 1개** — 읽기에 자연스러워서 틀려도 아무도 의심하지 않을 규칙.
  2. 주석과 코드가 다르거나 매직 넘버가 있는 규칙 1개.
  3. 확신도 "추정" 이거나 근거가 여러 파일에 걸친 규칙 1개.
- 각 추천에 "열어 볼 파일:줄번호"와 "확인할 질문 한 줄"을 붙인다. 점검 결과는 사용자가 알려 주면 `BUSINESS-RULES.md` 끝 "검증 이력"에 적는다.
